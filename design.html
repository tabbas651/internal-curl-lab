Standalone application / source walkthrough

What curl_probe.cpp does

A small application that configures libcurl similarly to AAMP's manifest downloader, runs the request in a separate thread, and measures how long curl and the caller's join take. It does not run AAMP or play video.

Run itAll arguments ThreadsFunctions and state Curl optionsRetries Logs and timingsResolver timing Limits
Current design: one client container, a URL supplied by you, and the container's configured DNS/network. No gateway container, manifest.test server, automatic ARP block or DNS block is required.

1. Start and run

Host terminal: start once and enter the client shell.

cd dns-curl-lab
docker compose up -d --build --remove-orphans
docker compose exec client sh

Client container shell: use an approved reachable endpoint. This public example is not the original incident's manifest.

curl-probe --url https://example.com/ --verify-peer
echo "probe_exit=$?"

curl-probe --url https://example.com/ --verify-peer --stop-after-ms 1000
echo "probe_exit=$?"

The first command waits for natural completion. The second requests stop after approximately one second if the worker has not finished. No default URL is compiled into the application. To test Google explicitly, use --url https://www.google.com/.

The executable is /usr/local/bin/curl-probe; any working directory inside the client shell is fine. This performs an HTTP GET, not ping.

2. Every command-line argument

Options are parsed by arguments(). All options except --help, --verify-peer and --verbose require a following value. Quote URLs or header values containing shell characters or spaces. Repeated headers accumulate; other repeated value options use the last value. Unknown options, missing values and invalid numbers exit 2.

ArgumentDefault / accepted rangeWhat it changes and example
--url URLRequired; nonemptySets Config::url and CURLOPT_URL. Hostname lookup is done by libcurl, not by application code. Example: --url https://example.com/. The parser does not validate the URL format; curl reports URL errors.
--timeout SEC20 seconds; 0-3600Sets CURLOPT_TIMEOUT, the total transfer timeout per curl attempt. Zero disables that timeout. Retries can increase overall application duration; resolver cleanup can also delay return. Example: --timeout 20.
--connect-timeout SEC10 seconds; 0-3600Sets CURLOPT_CONNECTTIMEOUT for the connection phase, including name resolution and connection/protocol establishment. It is not TCP-only. Zero selects libcurl's default connection timeout, not an unlimited timeout. Example: --connect-timeout 10.
--dns-cache SEC180 seconds; 0-86400Sets CURLOPT_DNS_CACHE_TIMEOUT, how long libcurl caches lookup results. Zero disables this cache. Does not set DNS query timeout or edit resolv.conf. Fresh application runs do not share this easy-handle cache. Example: --dns-cache 180.
--stop-after-ms MSOmitted: -1 internally; explicit 0-3600000 The caller waits for worker completion for this many milliseconds, then clears the active flag if still running. Measured from the caller's wait after thread creation, not DNS entry or perform_begin. Zero requests cancellation immediately if the worker is not already done. Not a hard kill or join deadline. Example: --stop-after-ms 1000.
--start-timeout SEC0 (disabled); 0-3600 Application progress callback aborts if no response body bytes have arrived by this elapsed time in an attempt. Header arrival alone does not satisfy it. Only checked when curl invokes the callback; not an independent timer thread. Example: --start-timeout 5.
--stall-timeout SEC10 seconds; 0-3600 After at least one body byte, progress callback aborts if no body update has occurred for this interval. Zero disables it. It does not apply before the first body byte. Example: --stall-timeout 10.
--retries N1; 0-100Retry budget for curl timeout/connect/send failures and selected HTTP errors. One means at most two attempts for these errors. Zero disables ordinary retries, but HTTP 408 still has a forced minimum retry and HTTP 502 uses its separate budget. Example: --retries 0.
--retry-502 N10; 0-100Separate retry budget when HTTP status is 502. Ten allows up to eleven attempts; retry delay is one second. Example: --retry-502 0.
--user-agent TEXTAAMP-DNS-Lab/1.0 Sets CURLOPT_USERAGENT. The default is a lab placeholder, not the device's actual browser/player identity. Example: --user-agent "MyTestAgent/1.0".
--header TEXTNo custom headersAdds a header to the curl list via CURLOPT_HTTPHEADER. Repeat for several headers. Example: --header "Accept: application/dash+xml". Verbose traces can expose these values; never share production tokens.
--proxy URLEmpty string: no proxySets CURLOPT_PROXY. Empty explicitly disables environment proxies. Using a proxy can change where DNS occurs, so keep it constant in comparisons. Example: --proxy http://proxy.example:8080. This example is a placeholder and must be replaced.
--verify-peerOff; flag takes no value Enables both certificate-chain validation (SSL_VERIFYPEER=1) and hostname validation (SSL_VERIFYHOST=2). Off matches the supplied incident configuration, but is unsafe for ordinary HTTPS traffic. Recommended for public endpoints. Do not write --verify-peer true.
--verboseOff; flag takes no valueSets CURLOPT_VERBOSE=1. Libcurl writes diagnostic output to stderr, separate from application events on stdout. Useful for DNS/connect/TLS details; may expose URLs and headers.
--helpNo valuePrints usage and exits 0 without curl initialization or a worker. Help displays [--url URL], but the actual parser requires a URL for a run.
Timeout settings are different layers: curl total/connect timeouts, callback start/stall checks, and glibc retries in /etc/resolv.conf. None of the probe arguments changes resolv.conf or blocks ARP/DNS.

3. Two application threads

Caller: main()

  1. Parse arguments; initialize libcurl globally before starting the worker.
  2. Log the runtime version, AsynchDNS feature, c-ares version and selected settings.
  3. Create std::thread worker(download, std::ref(state)). State is shared by reference and remains alive until join completes.
  4. If a stop delay is given, wait on doneCondition. If the worker finishes, log completed_before_release. Otherwise log release_requested and set active=false.
  5. Log join_begin and wait in worker.join(). There is no timed join.
  6. Log join_end, clean up libcurl globally and return the worker result.

Worker: download()

  1. Create one CURL easy handle and the optional custom header list.
  2. Apply curl options and point callback userdata at shared State.
  3. Reset per-attempt byte/timing fields and call curl_easy_perform synchronously.
  4. Curl invokes receive/header/progress callbacks on this worker's request path. A threaded DNS backend may create an additional internal resolver thread.
  5. When curl returns, log result and getinfo timings, then decide whether to retry.
  6. Clean up the easy handle and header list, publish done=true and notify the caller.
Possible delayed stop:
Caller joins worker
  Worker remains in curl_easy_perform / internal resolver cleanup
    Internal DNS thread remains in getaddrinfo

active=false requests cancellation; it does not forcibly stop that DNS thread.

Without a stop delay, join_begin may precede perform_begin because the caller and worker are scheduled independently. That ordering is normal, not evidence of deadlock. The stack-local State is not destroyed while the worker uses it.

4. Functions and shared state

CodeResponsibility
ConfigStores CLI settings, defaults, URL, proxy and header values.
StateShared request state: config; monotonic origin; attempt start and last body update; active cancellation flag; byte count; completion condition and result.
milliseconds()Converts time since a steady_clock timestamp to milliseconds. It is elapsed time, not a UTC date.
event()Locks logMutex so application log lines from caller/worker do not interleave; prints elapsed_ms and flushes stdout.
number()Parses an integer using stol, rejects unconsumed characters and out-of-range values. Parsing exceptions become exit 2.
arguments()Maps CLI options to Config; requires a URL.
receive()Body callback: computes size * count, increments bytes, updates the last-data timestamp and discards content. Returns the consumed byte count to curl.
receiveHeader()Header callback: discards header content and returns size * count. It does not update body stall timing.
progress()Checks release flag first, then no-body start timeout, then post-body stall timeout. Returns 1 to abort, 0 to continue. The curl_off_t progress counters are intentionally unused.
option()Wraps curl_easy_setopt. A configuration failure throws rather than silently continuing; worker logs event=error.
download()Owns curl handle/header list, attempts, retry policy, result metrics and worker cleanup.
main()Initializes the library, schedules optional stop, joins the worker and returns the process exit status.

active is atomic for cross-thread cancellation. doneMutex and doneCondition protect completion signaling. Worker-only fields such as bytes, updated and cancelled are not modified by the caller. The cancelled field suppresses repeated release_flag log messages; it is not the final curl status.

5. Fixed curl options and callback wiring

OptionValue / meaning
CURLOPT_HTTPGET1: request body using HTTP GET, not POST or ping.
CURLOPT_NOSIGNAL1: libcurl avoids signal-based operations. Does not suppress all signals to the process, choose c-ares, or cancel DNS.
CURLOPT_IPRESOLVEWHATEVER: permits both IPv4 and IPv6 according to backend/platform behavior. Does not guarantee both queries every run.
CURLOPT_FOLLOWLOCATION1: follow HTTP redirects. Redirects may involve another host and additional DNS/connection work.
CURLOPT_ACCEPT_ENCODINGEmpty string: request all encodings supported by the library and enable automatic decoding.
CURLOPT_PROXYAUTHCURLAUTH_ANY: allow supported proxy authentication negotiation when using a proxy.
CURLOPT_SSLVERSIONTLSv1_2: TLS 1.2 minimum, not a forced TLS-1.2-only maximum. Relevant only for TLS connections.
CURLOPT_NOPROGRESS0: enables progress callback processing.
XFERINFOFUNCTION / XFERINFODATAprogress function and pointer to State. curl_off_t parameters match libcurl's callback ABI.
WRITEFUNCTION / WRITEDATAreceive function and State pointer for response body accounting.
HEADERFUNCTION / HEADERDATAreceiveHeader function and State pointer. Header content is not stored.

The configurable curl options are covered in the argument table above. There is no CURLOPT_RESOLVE override, dedicated DNS-server option, multi API loop, or direct getaddrinfo call in this application. DNS is handled by libcurl and its configured backend.

6. Exactly when it retries

After every perform return, attempt is compared with the retry budget. With a budget N, up to N+1 attempts are possible for retry-worthy results.

ResultProbe behavior
Curl OK, HTTP 2xxSuccess, no retry, exit 0.
Curl OK, HTTP 408Ordinary retry budget; forced to 1 if set to zero. Sleep 50 ms before retry.
Curl OK, HTTP 502Uses --retry-502; sleep 1,000 ms before retry.
Curl OK, other HTTP status at least 500Uses --retries; sleep 50 ms before retry.
Curl 28 / 7 / 55Operation timeout / could not connect / send error: uses retry budget, no added retry sleep.
Curl 6Could not resolve host: no retry in this probe.
Curl 42Aborted by callback: no retry.
Other curl errors or HTTP failuresNo retry; exit 1.

The active release flag is not checked independently at the retry-loop boundary. If curl returns a retry-worthy timeout after release, another attempt may start; its progress callback can then abort. This preserves the relevant AAMP-style retry behavior rather than adding a new cancellation guarantee.

20 seconds is an attempt timeout, not an application deadline. Two attempts, DNS cleanup, HTTP retry waits and final handle cleanup can all increase total time. Do not infer getaddrinfo duration just from the budget.

7. Read the log events and timing fields

EventMeaning
runtimeActual libcurl version/features and selected total/connect/cache settings. AsynchDNS=yes alone does not distinguish threaded glibc resolution from c-ares; inspect c_ares and trace behavior.
perform_beginAn attempt is about to enter curl_easy_perform, with attempt number.
release_requestedCaller logs intent to stop, then clears active. The worker may not observe it immediately.
progress_abortCurl invoked the callback and it requests abort. reason is release_flag, start_timeout or stall_timeout.
perform_returnThe synchronous curl call has returned; metrics and curl/HTTP status are recorded.
cleanup_beginWorker is about to clean up the handle and header list. Cleanup time is outside perform wall_ms.
worker_exitCleanup completed; worker is about to publish done and finish. Actual thread return occurs shortly afterward.
completed_before_releaseWorker finished before the scheduled cancellation; no release flag was set.
join_begin / join_endCaller enters/leaves join. wait_ms measures the wait starting just before join_begin logging.
errorWorker exception, such as curl option setup/allocation failure; exit 2. Parser errors print to stderr before startup.
  • elapsed_ms: monotonic time from State construction, including argument parsing and global curl setup. Not UTC time.
  • wall_ms: measured around each curl attempt; includes internal work performed before curl_easy_perform returns. Includes a small logging overhead.
  • namelookup_s: CURLINFO_NAMELOOKUP_TIME, curl's completed name-lookup timing. Zero on a failed lookup does not prove DNS was instant.
  • connect_s: CURLINFO_CONNECT_TIME, cumulative time from request start until connection establishment, not a standalone TCP duration.
  • curl_total_s: CURLINFO_TOTAL_TIME reported by curl for the attempt. It need not equal the application's measured wall time.
  • curl_code: CURLcode, separate from HTTP status. http=0 commonly means no HTTP response was obtained.
Illustrative delayed-cancellation example (not a new measurement):
elapsed_ms=1000  event=release_requested
elapsed_ms=1015  event=progress_abort reason=release_flag
elapsed_ms=6145  event=perform_return ... curl_code=42
elapsed_ms=6150  event=join_end ...

Release-to-join = approximately 5150 ms.
Callback-to-curl-return = approximately 5130 ms.
Neither alone proves all that time was spent in getaddrinfo.

Use packet captures and strace to attribute the delay. Without cancellation, join wait includes normal transfer time. With cancellation, join wait starts after the caller requested release and is close to, but not exactly, total release-to-join latency. Compare elapsed_ms timestamps for that exact interval.

Process exit status

0 = last attempt was curl OK and HTTP 2xx, or --help
1 = last attempt failed HTTP/curl or was cancelled
2 = argument/setup/worker exception failure

This probe evaluates HTTP responses: a successful file:// transfer has no HTTP 2xx status and therefore exits 1. Use HTTP/HTTPS for the intended test.

8. Measure the actual getaddrinfo call

The optional resolver_trace.c wrapper is built as /usr/local/lib/libresolver_trace.so. Run inside the client:

LD_PRELOAD=/usr/local/lib/libresolver_trace.so curl-probe --url https://example.com/ --verify-peer --stop-after-ms 1000
echo "probe_exit=$?"

It intercepts the dynamically linked getaddrinfo symbol and forwards the same arguments to the real implementation using RTLD_NEXT. It does not change DNS answers, timeout settings or AAMP-style curl options.

Resolver fieldMeaning
resolver_event=beginResolver entry; records hostname, service, tid, requested family and monotonic timestamp.
resolver_event=endResolver returned; same tid, return timestamp, duration_ms, status and errno.
tidLinux thread ID; locate this thread in strace to inspect DNS socket operations and poll waits.
duration_msElapsed getaddrinfo time, including NSS and DNS processing, not just network packet time. Logging adds overhead.
status0 is success; nonzero is an EAI error, not a curl error. errno is relevant for EAI_SYSTEM only.
monotonic_msAbsolute CLOCK_MONOTONIC reading; not the same origin as the probe's relative elapsed_ms or strace wall timestamps.

The healthy validation observed getaddrinfo returning successfully in 624.8 ms. Curl was subsequently cancelled with code 42 after the one-second stop request. This is one lab measurement, not a device timeout guarantee.

strace -f -ttt -T -o /results/trace.txt -e trace=network,poll,ppoll,select,pselect6,futex env LD_PRELOAD=/usr/local/lib/libresolver_trace.so curl-probe --url https://example.com/ --verify-peer --stop-after-ms 1000

-T measures individual syscalls; -f follows resolver threads. Match the wrapper tid to DNS socket activity and poll calls. Other threads also poll. The wrapper logs to stderr and the probe logs to stdout; both can be saved separately as described in the README.

A begin without an end shows an outstanding call, not a complete measured duration. No events can indicate caching, a literal IP, c-ares or another non-intercepted path. LD_PRELOAD tracing requires dynamic linking and is observational, with some timing overhead.

9. What this test does not establish

  • The probe alone measures curl; the optional wrapper measures intercepted getaddrinfo calls. strace is needed to attribute individual DNS poll waits.
  • No automatic edits to resolv.conf, ARP blocking, DNS blocking or WPE crash recovery.
  • No complete AAMP object lifecycle, manifest refresh/parsing, two MPD downloaders, notifier thread, DRM or media pipeline.
  • No guarantee that Ubuntu's libcurl behaves like the device's vendor build.
  • No permanent fix is implemented; this application reproduces and measures the relevant execution pattern.

For resolver changes, packet capture commands and restoration, use the current README. Review the implementation directly in curl_probe.cpp, or the single-container setup in compose.yaml.
